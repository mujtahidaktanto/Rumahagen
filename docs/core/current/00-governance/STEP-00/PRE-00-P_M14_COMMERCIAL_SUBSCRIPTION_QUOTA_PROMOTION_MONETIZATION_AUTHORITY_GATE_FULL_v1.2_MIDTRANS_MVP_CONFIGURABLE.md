## 47A.3 Admin vs Superadmin vs Manager

### Superadmin

**Commercial configuration authority: ALL within M14 governance**,
including:

-   create/update/deactivate commercial Catalog entries;
-   create/update/deactivate Offers;
-   create/update/manage Subscription plans;
-   configure commercial Entitlement definitions and benefit rules;
-   configure Quota Capacity, configurable grants/bonuses, and
    commercial allowance parameters;
-   create/update/activate/deactivate Promotions;
-   manage commercial configuration lifecycle;
-   review/execute governed commercial reconciliation actions where
    assigned by M09/M14 governance;
-   perform administrative override only where a specific M14 capability
    and governance rule explicitly permits it.

Superadmin does **not** gain authority to rewrite the meaning of
historical commercial snapshots or silently mutate historical purchases.

### Admin

**Commercial configuration authority: MANAGE within the approved M14 MVP
configuration surface.**

Admin may, subject to M10 permission/scope/condition enforcement:

-   create and edit approved Catalog/Offer configurations;
-   create and manage Subscription configurations;
-   configure commercial Entitlement definitions/benefit mappings;
-   configure Quota Capacity and approved grant/bonus/allowance
    parameters;
-   create, edit, activate, deactivate, and manage Promotions;
-   view commercial configuration and operational commercial state;
-   execute only the M14 commercial operations explicitly granted by the
    permission matrix.

Admin does **not** automatically receive:

-   generic Superadmin bypass;
-   unrestricted historical transaction editing;
-   arbitrary entitlement issuance outside approved M14 rules;
-   arbitrary quota balance mutation;
-   arbitrary usage deletion;
-   authority to change a historical commercial snapshot;
-   authority to redefine M10 authorization/RLS;
-   authority to change provider secrets/ownership;
-   authority to change M14 ownership boundaries.

### Manager

**Default commercial configuration authority: REVIEW / OPERATIONAL
GOVERNANCE, not unrestricted configuration ALL.**

Manager may perform only specifically granted M14 review, operational,
reconciliation, or other commercial capabilities. Manager does not
receive automatic authority to create/edit/activate all commercial
configurations.

A future Manager configuration capability may be delegated only through
the M10 permission model without changing the M14 commercial authority
boundary.

## 47A.4 Subscription Configuration Rules

Subscription configuration is **definition/configuration**, not
historical purchase mutation.

Admin/Superadmin may configure, subject to authorization:

-   subscription plan identity;
-   display name/description;
-   active/inactive lifecycle;
-   validity/term parameters;
-   commercial price;
-   included commercial benefits;
-   included quota/capacity entitlements;
-   included allowances such as approved Refresh allowance where
    applicable;
-   feature/benefit mapping that is already permitted by the M14 model.

Rules:

1.  New configuration affects eligible new commercial transactions
    according to its effective lifecycle.
2.  Existing completed purchases retain their historical commercial
    meaning.
3.  Editing a live plan must not silently rewrite an already-created
    Commercial Snapshot.
4.  Deactivation prevents new use according to lifecycle rules but does
    not erase historical purchases or active entitlements that were
    legitimately granted.
5.  Subscription configuration cannot create an authorization permission
    or RBAC role.
6.  Subscription entitlement does not itself grant access; M10
    authorization remains required for protected capabilities.

**Classification: AUGMENT / MANDATORY PROPAGATION**

## 47A.5 Commercial Entitlement Configuration Rules

Commercial Entitlement has two distinct concepts:

**Entitlement Definition** = configurable rule/benefit definition.

**Entitlement Instance** = the concrete benefit granted to an
account/entity after successful commercial fulfillment.

Admin/Superadmin may configure approved entitlement definitions and
their benefit mappings.

They may **not** bypass the fulfillment boundary merely by editing a
configuration record.

Rules:

1.  Entitlement definitions may map an approved commercial purchase to
    an approved benefit.
2.  Entitlement instances arise from valid fulfillment according to M14
    rules.
3.  Direct manual entitlement issuance, if ever needed for
    reconciliation, must be a distinct governed M14 reconciliation
    capability with evidence and provenance; it is not implied by
    ordinary configuration permission.
4.  Entitlement does not equal RBAC permission.
5.  Entitlement does not override M10 authorization.
6.  Historical entitlement provenance must remain reconstructable.

## 47A.9 Commercial Snapshot --- Immutable Historical Boundary

-   historical promotion benefit;
-   historical subscription/add-on terms;
-   historical quota/benefit basis;

## 71A.2 MVP Checkout Interface --- Snap

Based on the uploaded Midtrans API documentation, **Midtrans Snap is
selected as the MVP checkout interface**, while the RumahAgen
commercial/payment contract remains provider-agnostic.

The source distinguishes:

-   **Snap** --- built-in/hosted checkout interface, supporting pop-up,
    embedded, or redirect presentation; the source describes it as quick
    to integrate and supporting the available Midtrans payment methods
    through one integration.
-   **Core API** --- RESTful custom-interface integration where
    RumahAgen builds the payment UI itself.

For the MVP, Snap is therefore the default implementation path because
it reduces payment UI implementation complexity while preserving the M14
commercial model.

Core API is **not deleted or prohibited**. It remains a possible later
implementation where RumahAgen requires deeper custom payment
UI/control.

## 71A.3 Provider Rules Adopted for MVP

The following provider rules from the uploaded Midtrans documentation
are adopted as the implementation constraints for the MVP:

1.  **Backend-only Server Key**
    -   Server Key is secret.
    -   Backend requests use the Server Key through Basic Authorization.
    -   Server Key must never be exposed to public frontend/browser
        code.
2.  **Client Key boundary**
    -   Frontend Snap integration uses the Client Key as required by the
        provider-side checkout library.
    -   Client Key does not replace or expose the Server Key.
3.  **JSON API contract**
    -   Backend API requests use `Content-Type: application/json`.
    -   API responses are handled as JSON with
        `Accept: application/json`.
4.  **Snap transaction creation**
    -   The backend creates the Snap transaction token.
    -   The transaction request includes a unique `order_id` and integer
        `gross_amount`.
    -   The provider documentation specifies permitted `order_id`
        characters as alphanumeric, `-`, `_`, `~`, and `.`, with a
        maximum length of 50 characters.
5.  **Environment separation**
    -   Sandbox and Production are separate environments.
    -   Sandbox credentials/endpoints must not be treated as Production
        credentials/endpoints.
    -   Production activation/configuration remains a separate
        operational readiness step.
6.  **Customer checkout**
    -   The customer completes payment through Snap.
    -   Frontend callbacks such as `onSuccess`, `onPending`, `onError`,
        and `onClose` are UX/event signals only and are **not** the
        authoritative RumahAgen payment confirmation.
7.  **Server-side notification**
    -   Midtrans HTTP notification is received by the RumahAgen backend.
    -   Payment state must be processed through the trusted verification
        boundary before M14 fulfillment/entitlement is executed.
8.  **Signature verification**
    -   Notification integrity must be checked using the provider's
        `signature_key` mechanism based on `order_id`, `status_code`,
        `gross_amount`, and Server Key, using the documented
        SHA512-based construction.
9.  **Notification acknowledgement / retry**
    -   The uploaded documentation states that HTTP 2xx is treated as
        successful notification receipt with no retry.
    -   It states that HTTP 500 is retried once.
    -   RumahAgen must therefore make notification handling idempotent
        and safe against repeated delivery.
10. **Tolerant notification parsing**
    -   The notification parser must tolerate new/unknown fields rather
        than failing merely because Midtrans adds fields.
11. **Order uniqueness**
    -   `order_id` must be unique for each RumahAgen commercial
        order/payment attempt according to the M14 order model.
    -   A provider error indicating an already-used/paid `order_id` must
        not be worked around by mutating an existing commercial order's
        historical identity. A new provider transaction identity must
        follow the approved retry/recovery model.
12. **Amount integrity**
    -   `gross_amount` must match the M14 commercial amount presented
        for the payment attempt.
    -   If `item_details` are used, the provider documentation requires
        the `gross_amount` to equal the sum represented by those item
        details.
13. **Payment-method availability**
    -   A payment method is only offered when enabled/available for the
        Midtrans merchant configuration.
    -   A provider response such as payment-type access denial is an
        integration/configuration condition, not a reason to alter M14
        commercial truth.
14. **Provider status is not M14 truth**
    -   Midtrans status/result is provider evidence.
    -   M14 decides whether the commercial transaction satisfies the
        RumahAgen fulfillment condition after trusted verification and
        the applicable business rules.
