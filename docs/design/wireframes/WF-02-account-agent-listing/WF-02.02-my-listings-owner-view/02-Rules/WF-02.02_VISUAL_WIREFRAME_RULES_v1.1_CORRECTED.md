# WF-02.02 — Visual Wireframe Rules v1.1 CORRECTED

## Source / authority
Uploaded sources only. M03 remains Listing/Refresh authority; M10 authorization; M12 organization/membership; M14 commercial entitlement; M11 public discovery.

## UX
- One coherent user goal per logical screen.
- Never force every requirement into one giant screen.
- Vertical scrolling is explicitly allowed and expected.
- Progressive disclosure is preferred for secondary/provenance content.
- State variants do not create scope expansion.

## Navigation
- Desktop navigation is collapsible/hide-show.
- Mobile uses drawer/menu.
- Navigation visibility is presentation only, never authorization.

## AGT-003
- Listing inventory is M03 projection.
- Lifecycle filters are presentation controls over authoritative state.
- Mobile transforms dense rows into cards/lists.
- Long lists continue vertically; pagination/infinite-scroll behavior is evidence/implementation-gated and not invented here.

## AGT-004
- Listing detail exposes lifecycle, ownership, visibility and authorized actions.
- State-specific variants must preserve Draft, Published, Expired, Suspended, Sold and Rented semantics.
- Ordinary edit is owner-only.
- Organization membership does not equal Listing ownership.
- After first successful publication, Address, Property Type, Land Size and Building Size remain visibly locked.
- Sold/Rented are historical Listing states and are not treated as current public search inventory.
- Suspended is enforcement, not normal publication approval.
- Normal publication has no Pending Review gate.
- Refresh remains a separate M03 action; commercial allowance remains M14-owned.

## Dynamic content / accessibility / responsive
- No new business character limits.
- Long text wraps naturally.
- Status uses text plus visual treatment, never color alone.
- Touch targets approximately 44×44 CSS px or larger.
- Keyboard focus and semantic labels are required.
- Desktop/mobile breakpoints are content-driven.
- No forced mobile horizontal overflow.

## Physical/runtime evidence — NON-BLOCKING / LOCKED
The absence of physical DB proof, migration proof, API runtime proof, RLS proof, runtime authorization proof, integration proof or production proof MUST NOT lock, HOLD, STOP or block WF-02.02 or any later WIRE package.

`NOT VERIFIED` is an evidence status, not a wireframe prohibition.

Only an unresolved semantic/authority/UX contradiction may block a WIRE package when truthful representation is impossible.

When implementation identifiers are not evidenced, use source-semantic labels and do not invent endpoints, IDs, tables, policies or runtime claims.
